# VEX

The CVE-2024-7347 VEX statement says: CVE-2024-7347 is **fixed** in **one
specific build of our image**, identified by its image digest.

| File | What it is |
|------|------------|
| `CVE-2024-7347.openvex.template.json` | The statement with placeholders for the image reference, digest, package purl and timestamp. This is the source of truth. |
| `CVE-2024-7347.openvex.json` | **Example**: the document generated for the author's build, `echo-nginx:1.25.5` with digest `sha256:39b97e573139adce9c1846d5dedfa72d50b94da43ec01b9cfff265a4ac7cd134`. It matches that build only. |
| `../reports/vex/CVE-2024-7347.openvex.json` | The document generated by the last `make vex`, for whatever image was built on that machine. |

## Why the VEX is generated per build

- **The statement must be scoped to an image digest.** `pkg:generic/nginx@1.25.5`
  alone would describe *every* nginx 1.25.5 binary, including the vulnerable one
  in `nginx:1.25-bookworm`. So the product is the image
  (`pkg:oci/echo-nginx@sha256:…`), and the nginx binary and our package are its
  subcomponents.
- **The digest changes with every rebuild.** The image build is not
  byte-reproducible: apt installs the current Debian package versions, and file
  timestamps differ. A reviewer who runs `make image` gets a different digest
  from the author's.
- **The author's document doesn't carry over.** Checked on a simulated rebuild:
  with the committed example, Grype still reports CVE-2024-7347 on the rebuilt
  image.

So `make vex` renders the template for the digest that is currently built,
then runs the demonstration with that document. The claim itself, "this build
has the backported patch", stays valid for any image built from this
repository: `make deb` fails unless the signature-checked patch applies, and
`make test` checks the patched behaviour. Only the identifier is
filled in per build.

Placeholders filled in by `tools/vex.mjs`:

| Placeholder | Source |
|-------------|--------|
| `{{IMAGE_REF}}` | `--image` (default `echo-nginx:1.25.5`) |
| `{{IMAGE_DIGEST}}` / `{{IMAGE_PURL}}` | `docker image inspect` → `RepoDigests` (the digest Syft records and Grype matches) |
| `{{DEB_PURL}}` | nginx package version and architecture (`dpkg-query`) and Debian version (`/etc/debian_version`) in the image |
| `{{TIMESTAMP}}` | Time of generation |

**Classic Docker image store.** Locally built images only get a repo digest
with Docker's containerd image store. That's the default in current Docker
Desktop / Docker Engine releases, and the one used here. With the classic store,
`RepoDigests` is empty and the statement cannot be scoped. `make vex` then
stops and explains how to switch.

### Statement fields

- **Status `fixed`, no `justification`.** OpenVEX only allows `justification`
  with status `not_affected`, and only from a fixed list of values. "Backported
  upstream patch" is explained in `status_notes`, together with the scope, the
  patch links (nginx.org + `build/patches/`), the build verification and the
  compatibility test check `cve-2024-7347`.

## Demonstration (`make vex`)

`make vex` (`tools/vex.mjs`) generates the document as above, then runs, for
our image and for `nginx:1.25-bookworm`:

1. a Syft SBOM of the image restricted to the binary cataloger
   (`--override-default-catalogers binary-classifier-cataloger`), which
   identifies `/usr/sbin/nginx` as `pkg:generic/nginx@1.25.5` with CPE
   `cpe:2.3:a:f5:nginx:1.25.5`;
2. Grype on that SBOM, without `--vex` and with `--vex` pointing at the
   generated document.

Outputs go to `reports/vex/` (the generated VEX, SBOMs, Grype JSON and table
output), with a summary in `reports/vex-demo.md`. The script fails unless all
five checks hold, including that **the VEX does not suppress the CVE on
upstream**.

Result for the author's build (2026-10-13, Syft v1.52.0, Grype v0.119.0,
grype-db v6.1.10):

| Image | `--vex` | CVE-2024-7347 | Matches |
|-------|---------|---------------|--------:|
| `echo-nginx:1.25.5` | no | **reported** on `pkg:generic/nginx@1.25.5` | 89 |
| `echo-nginx:1.25.5` | yes | not reported (in `ignoredMatches`, rule `vex: fixed`) | 88 |
| `nginx:1.25-bookworm` | no | **reported** | 131 |
| `nginx:1.25-bookworm` | yes | **still reported** (different digest, statement does not apply) | 131 |

The reviewer flow was also checked on a simulated rebuild (same nginx binary,
different digest). `make vex` generated a document for the new digest, and all
five checks passed.

## Why a binary-only SBOM

In the regular scans (`make scan`), neither scanner reports CVE-2024-7347 on
either image. They only see the Debian package `nginx` and match it against
Debian's records, which do not cover nginx.org builds. A full-image SBOM was
tried first (option 3) and does not work:

1. **Syft drops the binary by default.** It removes binary-classifier packages
   whose files are owned by an OS package. Turning that off
   (`SYFT_PACKAGE_EXCLUDE_BINARY_OVERLAP_BY_OWNERSHIP=false`) keeps
   `pkg:generic/nginx@1.25.5` in the SBOM.
2. **Grype drops it again.** It ignores binary packages that have an
   ownership-overlap relationship to an OS package. Omitting that relationship
   (`SYFT_RELATIONSHIPS_PACKAGE_FILE_OWNERSHIP_OVERLAP=false`) still gave no
   nginx match.
3. **Grype also drops the binary's CPE matches whenever an OS package with the
   same name is present.** This was confirmed with a scratch copy of the SBOM
   without the `nginx` deb entry: 21 nginx CVEs, including CVE-2024-7347.
   Nothing appears in `ignoredMatches`, even with
   `GRYPE_INCLUDE_MATCHER_SUPPRESSIONS=true`. Deleting a real package from an
   SBOM would make the SBOM false, so that copy was used for diagnosis only.

The fallback is a scan of the binary (option 2), but taken from the **image**
with Syft's binary cataloger rather than from an extracted file. The SBOM's
source is then the image, with its digest, which is what lets Grype apply the
statement to our image only. The binary-only SBOM claims nothing about the
Debian packages; those are covered by the regular scans in `reports/echo-*`.

The same binary scan also shows the residual nginx risk: 21 nginx CVEs for
nginx 1.25.5 on upstream, and 20 on our image once CVE-2024-7347 is
suppressed. That matches the residual list in `TRIAGE.md`.
